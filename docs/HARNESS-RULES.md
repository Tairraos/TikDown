# 存量项目 Harness 工程化规则

## 使用方法（先读这一节）

**这份文档是什么**：一份**自包含**的规则文档，用于把**已有代码库**改造为"智能体优先（Agent-First）"的 harness 工程化项目。它把改造所需的理念、五阶段流程、验收标准、模板全部写在本文里——**执行时不需要访问任何外部链接，也不需要原始资料**。

**本文档的定位是「施工图」，不是永久文件。** 施工期常驻在仓库里；竣工后按 **§14** 拆解归档——**不能中途删掉，也不能永远原样留着**。原因与操作见 §14。

> **本文参考了 OpenAI 官网的最佳实践文献《Harness engineering: leveraging Codex in an agent-first world》（中译《工程技术：在智能体优先的世界中利用 Codex》，2026-02-11）。** 该文献的全部可操作要点已内联到本文，无需另行查阅或访问原文。

**怎么用（四步）**

1. **放进仓库**：把本文档复制到目标仓库的 `docs/HARNESS-RULES.md`（或仓库根 `HARNESS-RULES.md`）。
2. **让 AI 读它并出计划**：新开会话，说下面这句话（可直接复制）：
   > 阅读仓库内的 `docs/HARNESS-RULES.md`，严格按其中的**第 5 节五阶段流程**对本项目执行 harness 工程化改造。  
   > 先只做**阶段 1**：全量扫描并输出《Harness 工程化改造计划》到 `docs/exec-plans/active/`，把问题清单写入 `docs/exec-plans/tech-debt-tracker.md`。  
   > **不要修改任何业务代码**，等我确认计划后再从阶段 1 开始落地。  
   > 扫描时按 **§3.2** 识别项目框架；若判定为 Tauri，进入阶段 3 时**必须按 §3.3 逐条向我提问**（是否生成 GitHub CI / 目标平台多选 / Release 直接发布还是出 draft），**问完再动手**。
3. **逐阶段推进**：计划确认后，按 1 → 2 → 3 → 4 → 5 顺序执行，每阶段按 §5 的验收标准逐条勾完再进入下一阶段。总验收见 §11。
4. **收官拆解**（五阶段全部通过后）：按 **§14** 把本文档拆开——一次性流程移入 `docs/exec-plans/completed/` 存档，长效契约抽进 `AGENTS.md` / `core-beliefs.md` / `ARCHITECTURE.md` 常驻。**本文档不是永久常驻文件，但五阶段没走完之前不要删、不要精简。**

**你（人类）在这套流程里的角色**：不写代码行。你负责四件事——**确认计划、回答决策问题、验收结果、确认收官拆解**。所有代码、配置、文档、CI 由智能体产出。

**本文档与其他文档的关系**：姊妹文档是《新建项目 Harness 工程化规则》（`new-project-harness-rules.md`），用于从空仓库开始建设。**改造存量项目用本文档，新建项目用那一份，不要混用。**

**版本**：v1.0 ｜ **适用范围**：任何已有代码库的改造 ｜ **总纲**：**人类掌舵，智能体执行。**

## 0. 执行契约（AI 必须遵守）

| 编号 | 契约                                                                   | 违反后果    |
| -- | -------------------------------------------------------------------- | ------- |
| C1 | **计划先行**：计划文档未获人工确认前，禁止修改任何业务代码。只允许新增文档类文件。                          | 视为返工    |
| C2 | **阶段串行**：五个阶段必须按 1→2→3→4→5 顺序执行，每阶段验收通过后才进入下一阶段。                     | 视为返工    |
| C3 | **不变量优先**：先建立"能被机械检查的约束"，再做重构。禁止在没有护栏的情况下大规模改代码。                     | 视为高风险管理 |
| C4 | **行为守恒**：重构不得改变原有业务行为。任何行为变更必须先在问题清单中显式登记并单独提交。                      | 严重缺陷    |
| C5 | **一切进仓库**：所有文档、清单、计划、测试、脚本必须是仓库内版本化的纯文本工件。禁止把关键信息留在对话、工单、外部文档或人的脑子里。 | 视为未交付   |
| C6 | **小粒度、可追溯**：每次提交只做一件事；提交历史必须能完整还原整个 harness 改造过程。                    | 视为未交付   |
| C7 | **不确定就提问**：遇到无法从仓库内推断的产品语义或业务意图，向人提问，不得自行猜测后改造。                      | —       |

**若规则与项目现状冲突**：以"不改变业务行为 + 提升可机械验证性"为裁决原则；无法裁决时列入计划的"待人工决策"清单。

## 1. 理念基线

### 1.1 定义

harness 工程化指的是：**把工程团队的主要工作从"写代码"转移到"设计环境、明确意图、构建反馈回路"**，使 AI 智能体能够在这个环境里可靠地完成工作。

三句话概括：

- **人类掌舵，智能体执行。** 人负责目标、边界、验收标准；智能体负责实现、验证、迭代。
- **瓶颈不再是编码速度，而是人类的注意力。** 因此所有能交给机械校验的东西，都必须机械校验。
- **软件工程仍然需要纪律，但纪律现在体现在"脚手架"上，而不是代码上。**

### 1.2 七条核心信条

| 编号 | 信条                    | 落地含义                                  |
| -- | --------------------- | ------------------------------------- |
| B1 | **给地图，不给说明书**         | 入口文件短小稳定，指向更深的真实来源；不要写一本 1000 页的手册    |
| B2 | **上下文是稀缺资源**          | 巨型指令文件会挤掉任务、代码和关键文档，让智能体抓错重点          |
| B3 | **智能体看不到的，就等于不存在**    | 知识必须在仓库里。Slack 讨论、外部文档、人的经验，对智能体全部不可见 |
| B4 | **强制执行不变量，而不是微观管理实现** | 规定"什么不许发生"，不规定"用什么库怎么写"               |
| B5 | **渐进式披露**             | 智能体从小而稳定的切入点开始，被逐步引导到下一层细节            |
| B6 | **技术债是高息贷款**          | 小额、持续、每日偿还，优于攒成大爆炸式重构                 |
| B7 | **纠错成本低、等待成本高**       | 高吞吐环境下，短生命周期 PR + 最小阻塞式合并门            |

### 1.3 实践上的取舍（直接复用）

- **偏好"无聊"的技术**：可组合性强、API 稳定、训练语料里常见的技术，智能体更容易建模。
- **允许重新实现功能子集**：若某个公共库行为不透明、上游难以绕过，自己实现一个行为完全可控、100% 测试覆盖的小版本，可能比适配它更便宜。
- **边界处解析数据形状**：数据进入系统时就要解析成明确的类型结构，不做"YOLO 式"直接探字段。
- **共享工具包优先于手写辅助函数**：把不变量集中在一处，而不是散落在各处。
- **优先选择能被完全内化、可在仓库内推理的依赖与抽象**。

### 1.4 存量项目的三条适配原则

原始实践的实验对象是一个空仓库，本项目是**存量代码库**。因此做三处调整：

1. **目标从"零人工代码"改为"智能体可读、可验证、可安全改动"。** 不追求代码由谁写，追求改动是否可被机械校验。
2. **改造必须按业务域分批推进。** 每个业务域独立完成"建地图 → 建不变量 → 重构 → 补测试"，禁止全仓大爆炸式改造。
3. **先给高风险、高频改动区域加护栏。** 护栏优先级 = 改动频率 × 故障代价。

## 2. 目标态：仓库知识布局规范

### 2.1 目录布局（目标态）

```text
AGENTS.md                          # 入口地图，约 100 行，不是百科
ARCHITECTURE.md                    # 领域与包分层的顶层地图
docs/
├── design-docs/
│   ├── index.md                   # 设计文档索引（含校验状态）
│   ├── core-beliefs.md            # 本项目的第一性原则
│   └── ...
├── exec-plans/
│   ├── active/                    # 进行中的执行计划（含进度与决策日志）
│   ├── completed/                 # 已完成计划归档
│   └── tech-debt-tracker.md       # 已知技术债台账
├── generated/
│   └── db-schema.md               # 由代码/DB 生成，禁止手改
├── product-specs/
│   ├── index.md
│   └── ...
├── references/                    # 外部依赖的可检索参考资料
│   └── ...
├── CI.md                          # CI 配置决定（见 §3，Tauri 项目必须建）
├── DESIGN.md
├── FRONTEND.md
├── PLANS.md
├── PRODUCT_SENSE.md
├── QUALITY_SCORE.md               # 按领域/架构层打分并追踪差距
├── RELIABILITY.md

```

**说明**：不必一次建全。按项目实际技术栈裁剪（例如无前端可去掉 `FRONTEND.md`），但 `AGENTS.md` + `ARCHITECTURE.md` + `docs/exec-plans/` + `docs/QUALITY_SCORE.md` 四件是必需项。

### 2.2 `AGENTS.md` 的写法

- **长度**：约 100 行。超过 200 行即为反模式，说明内容该被下推。
- **角色**：**目录**，不是百科。
- **目标形态见附录 E**（阶段 2 重写时直接照抄骨架）。
- **必须包含**：
  1. 项目一句话定位
  2. 常用命令（安装/构建/测试/lint/运行）
  3. 目录地图（各目录职责，一行一个）
  4. 硬约束清单（指向 §4 的不变量）
  5. 下一步去哪儿看（指向 `ARCHITECTURE.md`、`docs/design-docs/index.md`、`docs/exec-plans/active/`、`docs/CI.md`）
- **禁止包含**：教程式长文、逐文件说明、会过期的版本号清单、历史变更记录。

**为什么必须短**（内联来源经验）：

- 上下文是稀缺资源，巨型指令文件会挤掉任务本身与关键代码。
- 当一切都"重要"时，一切都不重要，智能体会退化成局部模式匹配。
- 单体手册会瞬间腐烂，成为陈旧规则的坟墓，且智能体无法判断哪条还有效。
- 单个大 blob 无法做机械检查（覆盖率、新鲜度、归属、交叉链接），漂移不可避免。

### 2.3 渐进式披露

智能体的加载路径应当是：`AGENTS.md`（100 行）→ `ARCHITECTURE.md`（分层地图）→ `docs/design-docs/*` 或 `docs/exec-plans/active/*`（具体任务上下文）。

任何一层都不应一次塞入全部细节。

### 2.4 文档防腐机制

- **机械校验**：用 linter / CI 作业检查知识库是否最新、是否交叉链接、结构是否正确。
- **文档园丁任务**：定期运行扫描任务，找出与真实代码行为不符的陈旧文档，并提交修复 PR。
- **规则升级路径**：当文档反复说不清时，**把规则提升为代码**（写进 linter、结构测试或类型定义）。

## 3. 项目框架识别与条件式 GitHub CI 配置

> **本节是强制流程，不是可选项。**  
> **在本文档流程中的位置**：**阶段 1** 的扫描子任务里完成框架识别（只收集信息）；**阶段 3** 的门禁审计里完成交互询问与 CI 落地（动手）。  
> 目的：为 Tauri 桌面项目一次性把打包发布链路定清楚；同时避免为非桌面项目生成一堆用不上的多平台打包流水线。

### 3.1 为什么必须先识别框架

CI 配置的形态**完全由框架决定**：

- **Tauri**（桌面应用）：需要多操作系统 matrix 构建、Rust 交叉编译 target、平台专属打包格式、Release 资产上传。
- **其他类型**（纯 Web / Node 服务 / CLI / 库 / 移动端 / 数据脚本）：`lint + test + build` 三件套即可，**不需要**多平台打包与 Release 流水线。

强行为非桌面项目生成桌面 CI，会带来：CI 永远红、无用文件污染仓库、后续维护者不敢删。

### 3.2 步骤 F1：识别项目框架（机械判定，不许靠猜）

扫描项目根目录，按下表判定。**满足任一证据即可判定为 Tauri**：

| 判定结果      | 判定证据                                                                                                                               |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **Tauri** | 存在 `src-tauri/tauri.conf.json`；或 `src-tauri/Cargo.toml` 的依赖中含 `tauri`；或根 `package.json` 的依赖含 `@tauri-apps/cli` / `@tauri-apps/api` |
| **其他**    | 以上均不命中                                                                                                                             |

**存量项目额外要查的两件事**：

1. **是否已存在 CI 配置**：列出 `.github/workflows/` 下现有文件及其触发条件。
2. **是否已有发布链路**：`package.json` 的 `scripts` 里是否已有 `release` / `build` 相关脚本；`src-tauri/tauri.conf.json` 的 `bundle` 配置现状；是否已配置签名密钥。

**输出要求**：把判定结果、命中证据、现有 CI 现状一并写进仓库文档（`docs/CI.md`，模板见 **附录 C**）。**不允许只在对话里说一句"这是 Tauri 项目"。**

### 3.3 步骤 F2：判定为 Tauri → 强制三步交互询问

**必须逐个提问，必须等用户回答后再继续。** 三个问题不得合并，不得替用户默认。

**提问前必须先做的事**：如果 `.github/workflows/` 下已有配置，**先把现状与差异摆给用户看**（现有文件、触发条件、构建平台、是否自动发布），让用户在知情的前提下回答，而不是当成从零开始。

---

**问 1｜是否为该项目生成 GitHub CI 配置（`.github/workflows/`）？**

- **「是」** → 继续问 2、问 3。若已有配置，同时确认是"生成新配置"还是"在现有配置上改造"。
- **「否」** → **跳过本节剩余全部内容**。在仓库文档中记录"用户于 `YYYY-MM-DD` 明确放弃 GitHub CI 配置"。**后续任何阶段不得静默补建。** 已有配置若需要清理，**必须先单独征求同意**再动。基础门禁（lint / test / build）仍按 §5 阶段 3 建立，只是不生成打包发布流水线。

---

**问 2（仅当问 1 = 是）｜CI build 需要产出哪些目标平台？〔多选〕**

- `windows`
- `mac`
- `ubuntu`

> 说明：可多选，也可只选一个。用户选几个就只配几个，**不要"顺便都加上"**。若现有配置已覆盖某些平台而用户未勾选，需明确确认"是否要移除"。

---

**问 3（仅当问 1 = 是）｜CI build 完成后，Release 如何发布？**

- **直接正式发布**：CI 构建完立即作为正式 Release 上线，访客可下载。
- **先出草稿（draft）**：CI 只创建草稿 Release 并上传资产，由用户自己在 GitHub 网页上检查后手动点发布。

> 补充说明（供你在回答前判断）：`mac` 在 CI 上分两种 CPU 架构（arm64 / x86_64），默认两者都构建；若只想出一份可另行说明。

---

**交互硬性约束**

- 用户未回答完三个问题之前，**不得新增或修改任何 `.github/workflows/` 文件**。
- 不得把三个问题合并成一次多选，不得给出"我建议默认全都要"之类的预设答案后直接动手。
- 用户只选部分平台时，matrix 只保留所选平台。
- 用户回答"否"之后，仍需在 `docs/CI.md` 记录该决定与日期。

**询问结果必须落盘。** 写入 `docs/CI.md`，模板见 **附录 C**。

### 3.4 步骤 F3：判定为其他类型 → 明确跳过

若 §3.2 判定为"其他"：

- **跳过整个 GitHub CI 小节**：不问 §3.3 的三个问题，不生成 `.github/workflows/` 的打包发布流水线。
- **基础门禁照建**：lint / test / build 三件套仍按 §5 阶段 3 落地。
- **照样记一条**：在 `docs/CI.md` 写下"框架判定 = 其他类型，本项不适用多平台打包与 Release 流水线"。
- **若项目已有 CI 配置**：只做审计（是否有效、是否腐烂、是否与代码现状脱节），审计结论写进问题清单；**不得因为"这段不适用"就顺手删掉现有配置**。

### 3.5 三个回答如何落到 CI 配置

| 用户回答         | 落点                                                                                     |
| ------------ | -------------------------------------------------------------------------------------- |
| **平台选择**     | `release.yml` 的 matrix 只保留所选 OS 的构建行                                                   |
| **直接发布**     | `tauri-action` 设 `releaseDraft: false`；guard job 追加 `gh release edit --draft=false` 兜底 |
| **先出 draft** | `tauri-action` 设 `releaseDraft: true`，由用户手动发布；guard 的 `--draft=false` 兜底**必须去掉**       |

> 具体 YAML 模板与实战坑清单见 **§10 Tauri 工程附加规范**。

## 4. 架构与品味不变量

### 4.1 分层领域架构（推荐目标模型）

**规则**：在每个业务域内，代码只能"向前"依赖一组固定的层：

```text
Types → Config → Repo → Service → Runtime → UI
```

- **横切关注点**（认证、连接器、遥测、功能开关）只能通过**单一显式接口**进入：`Providers`。
- **其他任何依赖路径都禁止**，并需通过自定义 linter + 结构测试**机械强制**。
- `Utils` 一类纯工具位于边界之外，只能向 `Providers` 供给。

> 这在人写的代码库里通常要等到几百名工程师才引入；对智能体协作而言，它是**早期前置条件**——有约束，速度才不会衰减，架构才不会漂移。

**存量项目适配**：若现有架构无法一步到位，先落地"依赖方向白名单 + 禁止跨域直连"两条，再逐步逼近理想分层。

### 4.2 品味不变量清单（建议逐项落地为 linter）

| 编号  | 不变量             | 机械检查方式                  |
| --- | --------------- | ----------------------- |
| T1  | 文件大小上限          | 行数/字节数阈值，超限即失败          |
| T2  | 结构化日志           | 禁止字符串拼接日志，强制结构化字段       |
| T3  | Schema 与类型的命名约定 | 正则校验命名模式                |
| T4  | 边界处解析数据形状       | 禁止直接读取未校验的外部结构          |
| T5  | 禁止"YOLO 式"探测数据  | 未通过类型/Schema 校验的字段访问即失败 |
| T6  | 共享工具优先          | 检测重复实现的手写辅助函数           |
| T7  | 依赖方向与允许的边       | 结构测试扫描 import 图         |
| T8  | 平台可靠性要求         | 检查超时、重试、优雅退出等必需模式       |
| T9  | 文档必填节与交叉链接      | 文档 lint                 |
| T10 | 覆盖率下限           | 覆盖率报告比对                 |

**自定义 linter 的硬要求**：因为规则是自定义的，**错误信息里必须写入修复指令**，让智能体读完报错就知道该怎么改。

> 在人优先的工作流里，这些规则可能显得迂腐；在智能体工作流里，它们是**倍增器**——一旦编码，就同时作用于所有地方。

### 4.3 约束的边界

参照大型工程平台组织的做法：**中央强制边界，本地允许自治。**

- 强约束：边界、正确性、可复现性。
- 弱约束：解决方案的表达方式。智能体产出的代码不必符合人类风格偏好，只要正确、可维护、对未来的智能体运行可读，即算达标。

### 4.4 人类品味的回流路径

评审意见、重构 PR、面向用户的缺陷，必须被固化为以下之一：

1. 文档更新，或
2. 直接编码进工具（linter / 结构测试 / 类型）。

**当文档反复说不清时，把规则提升为代码。**

## 5. 五阶段改造流程（核心）

### 阶段总览

### 阶段 1 · 全量扫描与问题清单

**目标**：在不改一行业务代码的前提下，把项目的真实状况变成一份可评审的计划。

**前置**：无。

**子任务**

1. **建立仓库地图**：识别顶层模块、包、构建产物、入口点、运行方式、部署方式；输出到计划的"项目概况"节。
2. **识别项目框架**：按 §3.2 判定项目类型（Tauri / 其他），列出命中证据；同时列出 `.github/workflows/` 现有配置与已有发布链路现状。**本阶段只收集信息，不做 CI 决策。**
3. **识别架构现状**：绘制模块间依赖关系（谁引用谁），标出循环依赖、越层依赖、跨域直连。
4. **度量复杂度**：找出超长文件、超大函数、深嵌套、高圈复杂度热点、God Object。
5. **识别重复代码**：跨模块重复逻辑、多份相似工具函数、复制粘贴式业务分支。
6. **盘点文档缺口**：无 README 的模块、与代码不符的说明、失效的注释与过期的配置示例。
7. **盘点测试缺口**：无测试模块、低覆盖区域、仅有 happy path 的关键路径、缺失的边界与异常用例。
8. **安全审计**：硬编码密钥/凭证、注入风险点、越权风险、依赖已知漏洞、日志泄露敏感信息。
9. **性能与可靠性审计**：N+1 查询、无界循环/无上限并发、缺失超时与重试、内存增长点、启动耗时。
10. **提交门禁现状审计**：现有 hooks、CI 流程、必需检查项、可否本地复现。
11. **风险分级与排序**：按"影响面 × 修复成本 × 改动风险"排优先级（P0/P1/P2 定义见附录 B）。
12. **制定分域改造批次**：把问题按业务域归集，排出改造批次与每批的验收条件。

**产出物**

- `docs/exec-plans/active/harness-migration.md`：改造计划，结构见 **附录 A**。
- `docs/exec-plans/tech-debt-tracker.md`：结构化问题清单，字段定义见 **附录 B**。
- `docs/CI.md`：框架判定结果与现有 CI 现状（**交互询问部分留到阶段 3**）。
- 分析脚本（若编写）纳入版本管理，放在 `scripts/analysis/` 下。

**验收标准**

- [ ] 五个阶段全部拆解完成，每个子任务都有：负责人角色、产出物路径、**可机械检查的**验收标准。
- [ ] **框架判定已完成，命中证据（文件路径）已写入 `docs/CI.md`。**
- [ ] 问题清单每条含：ID、位置（文件:行）、类别、严重度、证据、修复建议、**是否改变业务行为**。
- [ ] 明确标注"bug 修复"与"业务变更"两类，二者与纯重构严格分离。
- [ ] 每批改造都有独立的回滚方案。
- [ ] 计划文档中不存在只有标题、没有分析的条目。
- [ ] **未修改任何业务代码**（用 `git diff --stat` 自证）。


**禁止事项**

- 禁止在扫描阶段顺手修 bug。发现的问题一律先登记。
- 禁止在扫描阶段生成或修改 `.github/workflows/`。
- 禁止输出没有证据（文件路径/行号/度量数据）的问题条目。

### 阶段 2 · 文档对齐

**目标**：让文档与代码现状一致，并把仓库从"代码容器"升级为"记录系统"。

**前置**：阶段 1 计划已确认。

**子任务**

1. **重写 `AGENTS.md`**：按 §2.2 标准，压缩到约 100 行，改为地图形态。
2. **编写 `ARCHITECTURE.md`**：领域地图 + 包分层 + 依赖方向规则。
3. **建立 `docs/` 结构**：按 §2.1 裁剪落地；`index.md` 必须索引所有文档并标注校验状态。
4. **沉淀 `core-beliefs.md`**：把项目的第一性原则、架构取舍、命名与风格约定写死，作为后续一切争议的裁决依据。起草要点见 **附录 F**。
5. **清理过时内容**：删除失效文档；对无法判断的内容，先标注"待核实"并开 issue，不直接删除。
6. **把隐性知识搬进仓库**：把散落在对话、会议记录、个人笔记里的关键决策，转写为 `docs/design-docs/*` 的 Markdown。
7. **建立 `QUALITY_SCORE.md`**：按业务域和架构层打分（如测试覆盖、文档完备度、复杂度、依赖方向合规），并记录与目标的差距。
8. **建立 `docs/exec-plans/`**：迁移阶段 1 的计划与问题清单到标准位置；建立 `active/`、`completed/` 与 `tech-debt-tracker.md`。
9. **补全工程化说明**：本地开发、构建、测试、调试、发布、故障排查，全部写入 `docs/`。**Tauri 项目必须把发布链路（tag → CI → Release）写成文档。**
10. **建立文档防腐**：文档 linter（检查链接、必填节、新鲜度）+ 定期文档园丁任务。

**产出物**

- 修订后的 `AGENTS.md`、新增 `ARCHITECTURE.md`。
- `docs/` 目录树与全部索引文件。
- `docs/QUALITY_SCORE.md`、`docs/design-docs/core-beliefs.md`。
- 文档校验脚本 + CI 作业配置。

**验收标准**

- [ ] `AGENTS.md` ≤ 200 行，且不含教程式长文；能在 100 行内把智能体引到正确的下一站。
- [ ] `ARCHITECTURE.md` 的依赖方向规则与代码实际结构一致（抽样验证 ≥ 3 处）。
- [ ] `docs/index.md` 中的每个链接都可解析（机械校验通过）。
- [ ] 随机抽取 3 份旧文档，与代码逐条比对，无遗留错误描述。
- [ ] `QUALITY_SCORE.md` 对每个业务域给出分数与差距，且分数有可复算的依据。
- [ ] 文档校验 CI 在缺少必填节或出现死链时能失败。

**禁止事项**

- 禁止把文档写成代码的重复叙述（要写"为什么"和"边界"，不写"是什么"）。
- 禁止留下"待补充"占位而不开 issue 跟踪。

### 阶段 3 · 门禁审计与自动化质量校验

**目标**：让"项目可构建、质量可控"成为机器的事，而不是人的自觉。

**前置**：阶段 2 通过。

**子任务**

1. **执行 §3.3 三步交互询问**（仅当 §3.2 判定为 Tauri）：问"是否生成 GitHub CI"→ 问"目标平台多选"→ 问"Release 直接发布还是 draft"。**逐条问，等回答，落盘到 `docs/CI.md`。**
2. **按询问结果落地 CI**：Tauri 项目按 §10 生成 `release.yml` 与 `ci.yml`；非 Tauri 项目按 §3.4 跳过。
3. **盘点现有门禁**：列出全部 hook、CI 作业、必跑检查项，标注是否可本地复现。
4. **补齐基础门禁**：构建、类型检查、lint、格式化、单元测试、依赖漏洞扫描。
5. **加入提交前门禁**：本地 pre-commit / pre-push，确保明显问题不进仓库。
6. **编写架构结构测试**：用自动化方式校验分层依赖方向与允许的依赖边（见 §4.1）。
7. **编写自定义 linter 与品味不变量**（见 §4.2 的 T1–T10）：文件大小上限、结构化日志、命名约定、边界解析、平台可靠性要求。
8. **设计 linter 错误信息**：错误信息必须包含**修复指令**，便于智能体直接据此修正。
9. **加入文档门禁**：知识库新鲜度、必填节、交叉链接、索引完整性。
10. **加入覆盖率门禁**：整体下限 + 关键模块下限。
11. **建立门禁豁免机制**：豁免必须显式、带原因、带到期时间，且可被审计。
12. **固化合并理念**：短生命周期 PR + 最小阻塞式门禁；偶发失败的测试用后续重跑解决，而不是无限阻塞。

**产出物**

- `docs/CI.md`：框架判定 + 三问答案 + 落地说明（模板见附录 C）。
- **Tauri 项目**：`.github/workflows/release.yml`、`.github/workflows/ci.yml`。
- `docs/` 下的门禁清单文档（每项：检查名、触发时机、失败含义、修复指引）。
- CI 配置、hook 配置、自定义 linter、结构测试。
- 覆盖率配置与报告接入。

**验收标准**

- [ ] 若为 Tauri：**三个问题已逐条询问，`docs/CI.md` 已记录答案与日期；未擅自增加平台。**
- [ ] 若为 Tauri 且用户选"先出 draft"：**release 流程中不存在自动转正兜底**（实测检查配置文件）。
- [ ] 若非 Tauri：`docs/CI.md` 已记录"不适用"，且**未生成**任何打包发布流水线。
- [ ] 在干净环境执行"安装 → 构建 → 测试"可一次成功（有明确记录）。
- [ ] 故意引入越层依赖，门禁必须失败（**必须实测**，不能只看配置）。
- [ ] 故意超长文件、故意写非结构化日志，门禁必须失败（实测）。
- [ ] 故意留死链、删掉 `docs/index.md` 中的条目，文档门禁必须失败（实测）。
- [ ] 每个门禁失败时输出的信息都包含可执行的修复指引。
- [ ] 门禁可在本地一条命令复现，不依赖人为记忆。
- [ ] 全部豁免项都记录了原因与到期时间。

**禁止事项**

- 禁止在用户未回答三个 CI 问题前生成 `.github/workflows/`。
- 禁止因为"项目不是 Tauri"就顺手删掉现有 CI 配置（如需清理必须单独征求同意）。

### 阶段 4 · 问题修复与重构落地

**目标**：按计划分域推进，降低复杂度、拆分臃肿模块、消除重复，**同时不改变业务行为**。

**前置**：阶段 3 通过（护栏就位后才允许动业务代码）。

**子任务**

1. **按批次推进**：每批只处理一个业务域，批次切分依据阶段 1 的排序。
2. **拆分臃肿模块**：按职责切分，目标是每个模块/文件有单一且可命名的职责。
3. **落实单一职责**：把混合了 IO / 业务规则 / 编排的函数拆开。
4. **降低复杂度**：消除深嵌套（早返回）、消除布尔参数地狱、消除隐式状态。
5. **抽离公共可复用逻辑**：重复逻辑收敛到共享工具包，不保留多份手写辅助函数。
6. **修复问题清单中的缺陷**：严格按清单执行，P0 优先。
7. **同步更新文档**：每次改动同步更新对应文档、`index.md` 与 `QUALITY_SCORE.md` 的分数。
8. **同步维护计划**：在 `harness-migration.md` 中记录进度与决策日志；完成后移入 `docs/exec-plans/completed/`。
9. **更新技术债台账**：结清的移除，新发现的登记。

**产出物**

- 每个批次一组小粒度提交。
- 同步更新的文档与计划（进度、决策日志）。
- 更新后的 `tech-debt-tracker.md`。

**验收标准**

- [ ] 每个批次结束后：门禁全绿，测试全过。
- [ ] 重构行为守恒的证据：改动前后对相同输入产出相同结果（用测试或对拍脚本证明）。
- [ ] 所有业务行为变更与 bug 修复均在问题清单中显式标注，且**单独提交**。
- [ ] 重复代码度量下降（给出前后数值）。
- [ ] 文件/函数复杂度指标下降（给出前后数值）。
- [ ] 命中阈值的热点文件数量下降。
- [ ] 计划文档的进度与决策日志与提交历史一致（可逐条对应到 commit）。

**禁止事项**

- 禁止在一个提交里混合"重构"与"行为变更"。
- 禁止在没有测试保护的情况下重构关键路径。
- 禁止以"顺便优化"为由扩大改动范围。

### 阶段 5 · 测试补全与门禁接入

**目标**：为重构后的代码与原有缺失场景补齐测试，并把测试变成不可绕过的门禁。

**前置**：阶段 4 通过。

**子任务**

1. **补关键路径测试**：核心业务旅程必须端到端覆盖。
2. **补边界与异常测试**：空值、超限、并发、超时、部分失败、幂等性。
3. **补原有缺失场景**：阶段 1 清单中标记为"无测试"的模块逐一补齐。
4. **建立测试分层**：单元 / 集成 / 端到端，明确各层职责与运行时长上限。
5. **接入覆盖率门禁**：整体下限 + 关键模块下限，低于下限即失败。
6. **接入结构测试**：架构边界、命名约定、文件大小、依赖方向。
7. **消除不稳定测试**：识别 flaky 用例，修根因；短期可用重跑兜底，但必须登记。
8. **建立测试可维护性规则**：测试即文档——用例名描述行为，不使用魔法数字，不依赖执行顺序。
9. **把测试纳入同一套门禁**：新增测试不是"以后再说"，必须与重构同批交付。
10. **Tauri 项目补充**：Rust 侧单元测试 + 前端测试都要进 Verify 的两个 job；确保 macOS 原生测试 job 未被裁掉。

**产出物**

- 测试代码 + 测试数据 fixture。
- 覆盖率配置与报告。
- 结构测试与规范校验脚本。
- `docs/` 下的测试策略说明。

**验收标准**

- [ ] 覆盖率达成目标，且关键模块单独达标（给出报告）。
- [ ] 新增测试在**故意破坏实现**时必须失败（抽样验证 ≥ 3 处，防"假测试"）。
- [ ] 所有 P0 问题的修复都有对应回归测试。
- [ ] 全量测试在约定时长内跑完，且连续 3 次运行无失败。
- [ ] 覆盖率与结构测试均已接入门禁（实测：注入缺陷可被拦截）。
- [ ] 测试文件与文档一样纳入仓库版本管理（不得 gitignore）。

> **阶段 5 通过即达成 DoD（§11.1）。** 此时还有**最后一步**：执行 **§14 收官拆解**——把本文档里的一次性施工流程归档、长效契约迁移进常驻文档。**不要把它忘在脑后**，否则这套规则会以千行僵尸文件的形态永久留在 `docs/` 里。

## 6. 会话纪律（通用硬性要求）

> 以下三条适用于**所有项目**的每一次智能体会话，不区分技术栈；写入 `AGENTS.md` 承载为铁律。

### 6.1 版本一致性

- 前端、后端、根端各自的版本声明**必须始终一致**；任何一次版本变更同步更新所有声明点。
- Tauri 工程的三个声明点：`package.json` / `src-tauri/tauri.conf.json` / `src-tauri/Cargo.toml`。
- 用**脚本一次 bump 多处**（如 `scripts/_bump_version.py`），禁止手工散改其中一处。
- tag 发布时 CI guard 机械校验 `tag == package.json` 版本，不一致直接 fail——版本漂移在源头拦截。
- **改造期间新增该规范时，先对齐存量三处版本号**，再启用 guard，否则第一次 tag 就会红。

### 6.2 提交颗粒度：单一职责

- 一个改动会话内的提交按**单一职责原则**拆分：一次提交只做一件事（一个功能 / 一次修复 / 一次重构 / 一次文档更新）。
- Commit message 使用 Conventional Commits 前缀（`feat:` `fix:` `chore:` `docs:` `refactor:` `test:`…），body 详细说明动机、方案、影响面。
- 进行中的半成品按进度分次提交；普通提交不受测试与门禁阻塞。
- **会话结束前的最后一次提交必须通过全部本地门禁**，并在 message 注明 `[已测试]` / `[未测试]`。

### 6.3 用户提示词记录（`prompr-history.txt`）

- 仓库根维护一个 `prompr-history.txt`，**只给用户自己看**：
  - 加入 `.gitignore`，**不 push 到远程**；
  - 仓库内不放置任何"读取此文件"的要求或引用——智能体只追加，不读取、不合并。
- 每轮对话中，把用户提示词**结构化后追加到文件末尾**（纯 append，不读取已有内容做合并整理）：
  - 记录头：日期时间、模型名、agent 名字（运行环境取不到就省略该字段）；
  - 正文：按要点拆条记录提示词（保留原始语义与关键措辞，不改写意图）；
  - 每条记录末尾追加一行分隔线 `------`。
- **过滤规则**：提示词少于 10 个字的不记录（寒暄、单字确认类噪声）。
- 格式示例：

```text
[2026-10-02 11:17 CST] model=GLM-5.3-Flash | agent=ZCode
- 要求：对前后端与根端版本一致做要求
- 要求：改动的代码以单一职责为颗粒度多次提交
------
```

## 7. 提交与版本管理规范

### 7.1 分支

- 在新建的 `harnessing` 分支上实施，禁止直接在主干上改造。
- 每个阶段/批次可再开子分支，合并前必须过门禁。

### 7.2 小粒度提交

- 一次提交只做一件事。禁止"重构 + 改行为 + 调格式 + 改文档"混在一起。
- 提交顺序应当让每一步都保持可构建、可测试。
- 允许高频提交；短生命周期优于长周期大 PR。

### 7.3 Commit message

- 首行：`<类型>(<范围>): <一句话说明>`，例如 `refactor(order): 拆分 OrderService 的库存与结算职责`。
- 正文说明：动机、影响面、验证方式（跑了什么测试、什么命令）。
- 若涉及行为变更：明确写 `BREAKING` 或 `fix:`，并附问题清单 ID。

### 7.4 可追溯性（硬要求）

- `commit history` 必须能完整还原整个 harness 改造过程：从扫描、文档、门禁、重构到测试。
- 问题清单每条记录关联的 commit（可用 `Closes TD-XXX-NNN` 或提交正文引用）。
- 计划文档的进度日志逐条对应 commit。
- 所有文档、清单、测试文件纳入仓库版本管理。

### 7.5 合并理念

> 吞吐量改变合并理念。

- 采用**最小阻塞式**合并门：只拦真正危险的东西（编译失败、测试大面积失败、架构违规）。
- PR 生命周期短；偶发失败优先重跑，不无限阻塞。
- 前提是：纠错成本低、自动化程度高。若项目尚不满足该前提，先补齐门禁再放开。

## 8. 反馈回路与熵管理

### 8.1 标准 PR 循环

1. 人类描述任务，运行智能体，允许其打开 PR
2. 智能体**本地自审**自己的变更
3. 智能体在本地和云端**请求额外的、特定用途的智能体审查**
4. 智能体**响应所有人工或智能体的反馈**
5. 循环往复，直到所有智能体审查者满意

> 人类可以审 PR，但**并非必须**。随着时间推移，应把几乎所有审查工作调整为**智能体对智能体**。

### 8.2 熵与垃圾回收

**问题**：完全自主的智能体会**复现仓库中已存在的模式——包括那些不均衡或不够理想的模式**，随时间推移不可避免地导致漂移。（早期做法是每周五花 20% 时间人工清理"AI 残渣"，**不可扩展**。）

**解决方案**：把黄金原则编码进仓库 + 建立循环清理流程。

- 定期运行一组**后台智能体任务**：
  1. 扫描偏差（偏离黄金原则之处）
  2. 更新质量等级（`QUALITY_SCORE.md`）
  3. 发起**有针对性的重构 PR**
- 其中大多数 PR 应做到**一分钟内可审查并自动合并**。
- 另设 `doc-gardening` 任务，扫描过时文档并发起修复 PR。

**心智模型**：

> 其功能类似于**垃圾回收**。技术债就像一笔高息贷款：不断以小额贷款方式偿还，总比让债务累积后痛苦地一次性解决要好得多。

**目标节奏**：**每天**发现并解决不良模式，而不是让它们在代码库中传播数天或数周。

### 8.3 人类介入的正确姿势

人类始终参与，但抽象层次不同：**排定优先级、把用户反馈转化为验收标准、验证结果。**

当智能体遇到困难时，把它视为一个**信号**：识别缺失的东西——工具、指导、约束、文档——并将其反馈到仓库中，**且始终由智能体自己编写修复**。

## 9. 重构原则（红线）

| 编号 | 红线             | 说明                                 |
| -- | -------------- | ---------------------------------- |
| R1 | **保留原有业务行为**   | 重构的定义就是行为不变。                       |
| R2 | **行为变更显式登记**   | bug 修复与业务变更必须在问题清单中显式标注，并**单独提交**。 |
| R3 | **先护栏后动手**     | 没有测试和门禁保护的模块，先补保护再重构。              |
| R4 | **不做范围外优化**    | 发现的新问题登记进台账，不在本次提交里顺手处理。           |
| R5 | **不删无法判断的内容**  | 存疑的文档/代码标注"待核实"+ 开 issue，不静默删除。    |
| R6 | **不引入不可内化的依赖** | 优先可组合、API 稳定、行为可推理的依赖。             |
| R7 | **不藏信息**       | 关键决策必须落进仓库，不允许只存在于对话或人的记忆里。        |
| R8 | **每一步可回滚**     | 每个批次都要有明确回滚方式，并写进计划。               |

## 10. Tauri 工程附加规范

> **仅当 §3.2 判定为 Tauri、且 §3.3 问 1 回答"是"时适用。**  
> 下面每一条都来自真实发布链路的实战验证，照抄已验证结构，不要从零写。

### 10.1 tag 触发的多平台自动 Release

**workflow 固定结构**

1. **guard job**：校验 tag 版本与 `package.json` 一致；预建 Release（已存在则跳过，保留手写说明）。
2. **publish matrix（`fail-fast: false`）**：`macos-latest` × 2（aarch64 / x86_64，用 `--target` 分开构建）、`windows-latest`、`ubuntu-22.04`——**不要 `ubuntu-latest`**（Tauri 的 Linux 依赖按 22.04 包名安装）。**按 §3.3 问 2 的实际勾选裁剪 matrix，不要全部照抄。**
3. 每个 job 统一步骤：checkout → pnpm/action-setup → setup-node（cache pnpm）→ rust-toolchain（含 targets）→ `pnpm install --frozen-lockfile` → `tauri build` → 分平台上传。

**实战坑清单**（每条都真实翻过车）

- `bundle.targets` 必须为 `"all"`；写死 `["app"]` 会导致多平台 CI 只有 macOS 出包。
- **Windows 构建必需 `src-tauri/icons/icon.ico`** 并加入 `bundle.icon` 声明——macOS 本地构建碰不到该路径，首台 Windows CI 才暴露；用 `tauri icon <源图>` 生成，附带产物（Square* / Android / iOS 等）不入库。
- macOS 专属 API（`title_bar_style` 等）必须 `#[cfg(target_os = "macos")]` 隔离，否则 Windows 编译失败、Linux 直接报错；前端平台判断用 `userAgent` 而非编译期。
- 上传产物用 `find target -path '*/release/bundle/*'` 通配——带 `--target` 时产物在 `target/<triple>/release/bundle`，不带时在 `target/release/bundle`，两种都要覆盖；排除 deb 的 `control.tar.gz` / `data.tar.gz` 中间产物。
- 构建失败把日志尾部写成 `::error::` check-run 注解——无仓库管理员权限时 API 下载原始日志 403，注解是无认证可读的唯一排障通道。
- guard 预建 Release 后追加 `gh release edit --draft=false` 兜底：**删除旧 tag 重打会把已发布 Release 打回草稿**（对访客与匿名 API 不可见，而 `gh release view` 对草稿判定"已存在"而跳过创建，草稿将永远是草稿）。  
  ⚠️ **若 §3.3 问 3 用户选择"先出 draft"，此项兜底必须去掉**，否则会违背用户意图自动转正。
- 无 updater 配置时的完整资产 = 7 个：双 dmg + msi + setup.exe + deb / rpm / AppImage；`.app.tar.gz` / `.sig` 只在开启 updater 时产出。
- Verify（push 触发）建议双 job：frontend（ubuntu，前端检查 + 构建）+ native（macOS，原生测试 + 全套门禁）——**有 Rust 代码务必保留 macOS 原生测试 job**；tag 推送不跑 Verify，避免与 Release 双重编译。

**改造存量项目时的特别注意**

- 存量项目往往**已经有一份能跑的 `release.yml`**。此时第一步是**审计**（触发条件、平台覆盖、是否自动发布、有无草稿态兜底），把差异摆给用户，再决定"改造"还是"重建"。**不要直接覆盖。**
- 若现有配置与 §3.3 三问答案冲突（例如用户选了"只 build mac"，而现有配置跑四平台），必须显式确认后再裁剪。

### 10.2 构建目录与产物

- cargo 构建目录定位到**仓库根 `target/`**：`src-tauri/.cargo/config.toml` 设 `[build] target-dir = "../target"`。
- **注意 cargo 配置按 CWD 向上发现**：`cargo --manifest-path src-tauri/...` 从仓库根运行时读不到该配置，产物会落回 `src-tauri/target`；脚本内显式 `export CARGO_TARGET_DIR="$PWD/target"` 兜底。
- build 完成自动清理**可再生的临时产物**（`dist/`、`target/release/bundle/`）；**对下次构建有帮助的编译缓存一律保留**（`target/release`、`target/debug`），保证增量编译秒级完成。
- 本地 build 的 `.app` 产物**以版本号命名放在 `target/` 根**（如 `AppName_0.1.26.app`），只保留最新一份。


### 10.3 `package.json` 脚本（根）

- `build`：只在本地 build 出 app 产物（不打 dmg、不发布）。
- `release`：push 代码到远程，并对远程做 tag 动作——**先删除远程旧同名 tag，再打新 tag**（幂等重发）。
- 联动约束：正因 release 会删 tag 重打，CI guard 的草稿态兜底是**必需项而非可选项**（见 10.1），**除非**用户在 §3.3 问 3 明确选择了"先出 draft"。

## 13. 度量指标（建议纳入项目看板）

> 改造效果必须可度量，否则"改完了"只是主观判断。

| 指标                | 含义               | 方向      | 说明                     |
| ----------------- | ---------------- | ------- | ---------------------- |
| 人均日 PR 数          | 团队吞吐量            | ↑       | 改造后应明显上升               |
| PR 生命周期           | 从打开到合并的时长        | ↓       | 越短越好                   |
| 智能体自主完成率          | 无需人工判断即闭环的任务占比   | ↑       | 改造深度的核心体现              |
| 文档新鲜度             | 与真实代码行为一致的文档比例   | ↑       | 由文档门禁间接度量              |
| lint 违规数          | 违反品味不变式的存量       | ↓（趋近 0） | 阶段 3 建立基线，阶段 4 逐步压降    |
| AI 残渣清理量          | 每周期清理的偏差数        | 稳定高频    | 而非堆积后爆发                |
| 卡点转改进率            | 智能体卡点被转化为仓库改进的比例 | ↑       | 衡量反馈回路是否真的闭环           |
| **待办问题存量（P0/P1）** | 问题清单中未关闭的条目数     | ↓       | **改造专项指标**，P0 必须归零     |
| **热点文件数**         | 超阈值文件/函数的数量      | ↓       | **改造专项指标**，阶段 4 前后各测一次 |
| **覆盖率**           | 整体与关键模块覆盖率       | ↑       | **改造专项指标**，阶段 5 验收用    |

## 14. 本文档的生命周期与收官处置

> **一句话结论**：本文档是**施工图**——开工前读、施工中查、**竣工后拆解归档**。既不是用完即弃的临时文件，也不是永久常驻的百科。拆出来的两半必须分开处理：**一次性流程归档留痕，长效契约抽出常驻。**

### 14.1 三个阶段分别怎么处置

| 阶段 | 本文档在哪 | 谁读 | 动作 |
|---|---|---|---|
| **① 施工期**（阶段 1 起，至阶段 1–5 全部通过） | `docs/HARNESS-RULES.md`，**全文** | 你 + 智能体（**每次新会话都必须先读**） | **不删、不精简、不就地改写。** 它此刻是改造的入口规范 |
| **② 竣工时**（阶段 5 验收通过后那一次会话） | 同上 | 智能体执行拆解，你确认 | 按 §14.3 逐项拆解：一次性部分归档，长效契约迁移。**拆解单独一次提交** |
| **③ 竣工后**（常态开发） | 降级为 `docs/exec-plans/completed/harness-<YYYY-MM-DD>.md`，历史留痕、不再被常规加载 | 只在追溯"当初为什么这么定"时读 | 常驻入口改为 `AGENTS.md` + `core-beliefs.md` + `ARCHITECTURE.md` |

### 14.2 为什么"用完就删"和"永远留着"两头都不对

**不能删，三个理由**：

1. **决策依据会一起消失**。为什么这样分层、哪些平台要 build、发布走不走 draft、为什么把那次重构拆成三批——答案都在这份文档里。删掉之后，接手的人只能重新猜，而猜出来的方案大概率和现状不一致。
2. **反模式清单、重构红线、核心信条是长效资产**，不是施工期专属。
3. **很容易连母本一起删掉**（见 §14.5），那损失的不是一个项目，是模板资产本身。

**不能原样留，三个理由**：

1. **和本文档自己的要求直接冲突**。§2.2 要求 `AGENTS.md` 是**目录而非百科**，§2.4 还专门讲了文档防腐机制。一份逾 1000 行的 `HARNESS-RULES.md` 常驻在 `docs/` 里，本身就是第一个该被防腐机制处理的对象。
2. **一定会漂移**。改造完成后项目继续演进，实际做法会与文档逐渐分叉。没人维护的文档就是**僵尸文件**——而僵尸文件比没有文件更糟，它会让智能体照着错的规则干活。
3. **`docs/` 里每个常驻文件都是智能体的上下文成本**。§2.3 渐进式披露的前提是"入口足够小，深层内容按需下推"。

### 14.4 判据：一条规则该留还是该删

只问一句话：**它是"用来做决定的"，还是"用来约束日常的"？**

- **用来做决定的**（要不要 CI / build 哪些平台 / 正式发还是出 draft / 拆几批 / 每阶段验收什么）→ 决定做完了，答案已经**物化**在 `.github/workflows/`、`docs/CI.md`、目录结构里，文档里那份就成了重复信息。**归档。**
- **用来约束日常的**（不许跨层依赖 / 单文件不超 N 行 / 不许手写重复逻辑 / 每次提交单一职责）→ 天天都要用。**常驻，而且要以机器可检查的形式常驻。**

更强的判据：**能写成 linter 规则或结构测试的，文档里就不要重复写。** 文档只留"为什么"（进 `core-beliefs.md`），"怎么做"交给工具——这正是 §4.3「约束的边界」与原文"强制执行不变量，而非微观管理实现"的落地。

### 14.5 一个容易搞混的区分：母本 vs 副本

|  | **母本** | **仓库副本** |
|---|---|---|
| 是什么 | 本文档的**模板原件**，放在你的个人规则库／模板仓库里，**不在业务仓库** | 复制进每个待改造仓库的 `docs/HARNESS-RULES.md` |
| 生命周期 | **永久保留**，而且**每做完一个改造项目就回来迭代一次** | 按 §14.3 竣工归档 |
| 为什么 | 每改造一个项目都会踩到新坑（"CI 草稿态陷阱""版本 guard 先启用导致第一次 tag 就红"就是这么踩出来的），这些经验要回流母本，下个项目才不重踩 | 它服务的是这一个改造 |

**如果没有独立的模板仓库**：在业务仓库里把母本保留为 `docs/templates/HARNESS-RULES.md`，并在归档副本头部留一条指针指向它。**不要因为"用过一次"就把唯一的母本当垃圾扔了。**

### 14.6 收官动作（五阶段通过后执行）

阶段 1–5 全部通过后，在**同一次会话**里完成：

1. 按 §14.3 逐项拆解，产出 `docs/exec-plans/completed/harness-<YYYY-MM-DD>.md`。
2. **自检**：把本文档从仓库里拿掉，智能体仅凭 `AGENTS.md` + `core-beliefs.md` + `ARCHITECTURE.md` 是否仍能遵守**全部硬约束**？答"否"说明还有东西没迁移，回到第 1 步。
3. `git mv docs/HARNESS-RULES.md docs/exec-plans/completed/harness-<YYYY-MM-DD>.md`（用 `git mv` 保留历史）。
4. 归档文件开头加一行：`> 一次性施工图，已竣工归档。常驻规范见 AGENTS.md / core-beliefs.md / ARCHITECTURE.md。`
5. **单独一次提交**，如 `docs: 归档 harness 改造施工图，长效契约已迁移至常驻文档`。
6. **母本回流**：本次改造若发现本文档有缺口或错误，同步修正母本（§14.5）。

> **不要做的事**：第 2 步没通过就把本文档删掉。**文档退休的前提是它的职能已被工具和常驻文档接管**——没被接管的规则一旦删掉，就退化成口口相传。
